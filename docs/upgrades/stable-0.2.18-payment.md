## 本批行为变化

- EasyPay 由实际验签的 provider 查询确认商户、订单、金额和交易号；查询失败不履约，通知应重试。
- 新 pending 退款保留扣减；成功不再扣，失败在事务中归还并记审计。
  兼容旧 `DeductionRollbackOK` 与新 `DeductionHeld`。不可读审计必须停止自动终结。
- 支付宝保存退款请求号而非交易号；旧 pending 缺少请求号可能返回
  `REFUND_QUERY_UNSUPPORTED`，必须人工核对，不可猜号补写或重新退款。
  新请求查无记录的十分钟宽限期、未知请求时间均不得直接判失败。
- Stripe URL 不携带或信任 `client_secret`，只使用同订单本地恢复快照。
  本二开在目标上游之外做一处边界修正：把 localStorage 读取纳入已有
  try/catch/finally，存储被禁用时显示失败并结束 loading，不退回 URL secret。
  对应新增 `StripePaymentView.custom-security.spec.ts` 两个 storage-denial 回归。

## 开始前必须留存（仅在获得部署授权后执行）

先在脱敏的现有二开数据库副本演练。正式窗口必须冻结管理配置写入、用户流量、
支付创建、退款管理入口、所有轮询/恢复任务及所有旧 worker；排空在途请求。
外部通知到达时应由入口返回可重试失败，不可返回假成功、丢弃或只暂存于内存。
确认支付机构的重试时限及人工补单机制。**禁止新旧支付 worker 混跑。**
若不能证明迁移执行过程不会提前启动支付任务，保持入口关闭，先制定并演练隔离方案；
不能为触发迁移而把新旧 worker 同时拉起。

保存数据库可恢复备份、`schema_migrations` 全表、旧镜像 digest、配置版本、
分组开关/定价和支付订单/审计快照，并在隔离环境验证恢复。备份可能包含敏感
资料，只放受控加密位置；不要放 PR、日志或本仓库。连接认证使用受控 pgpass
或运维现有方式，禁止把密码写进命令行示例。

必须先完成[核心图片开关迁移门禁](stable-0.2.18-image-groups.md)，保留已禁用分组的策略。

## 支付逐单对账及回滚边界

1. 导出所有非终态支付/退款以及相关审计。按 provider、商户订单号、交易号、
   退款请求号逐单比对外部机构结果、余额或订阅扣减、审计与数据库状态。
   不把外部回执、secret 或完整商户配置写入 PR。
2. 明确区分旧 `DeductionRollbackOK` 与新 `DeductionHeld`；旧支付宝无法查询、
   缺失/损坏审计、金额不一致或状态不明的记录必须留在人工作业队列，禁止重发。
3. 验收重复/并发通知、错误商户/金额/订单号、查询超时、不泄露商户 key；
   余额及订阅 pending→成功/失败、事务失败、缓存失效和重复查询只扣/还一次。
4. 门户钱包充值/订阅→Stripe→返回、错单/过期恢复、URL 注入、存储拒绝、
   SDK 加载时离开及重复点击都要验证；不能只测上游独立页面。
5. 所有旧 worker 停止后才允许单版本启动；放流量前完成迁移、缓存与逐单对账。
   未解决订单应有明确冻结/人工处置策略和责任人。

**回滚不是换旧镜像。** 一旦新代码产生持有扣减的 pending，旧代码可能再次扣减。
先冻结支付与退款并保存证据，核对外部机构后选择前向修复或协调恢复。
数据库快照恢复不能撤销外部已经发生的付款或退款；禁止无条件回灌快照、改
审计 flag 或重复发起退款。旧二进制回退必须证明不存在不兼容 pending 语义，
并独立确认数据库、缓存和分组禁用策略兼容。
